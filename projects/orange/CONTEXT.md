# Контекст проекта Orange (для ИИ)

Общий контекст всего фреймворка — в [../../docs/CONTEXT.md](../../docs/CONTEXT.md). Прочитайте
его первым: там объяснено, почему `core/` не знает про Orange и что нельзя ломать при правках.
Этот файл — только про особенности конкретно этого проекта.

## Что тестируем

`https://my.orange.md/` — страница логина Orange (реальный, боевой сайт, не песочница).
Тестирование авторизовано владельцем проекта. Сайт сам делает редирект на `sso.orange.md`
после загрузки формы — это ожидаемое поведение, не баг.

Два независимых теста:
1. **UI-смоук с реальным входом** (`tests/ui/login-form.spec.ts`) — открывает форму логина,
   проверяет 9 элементов формы (заголовок, поля email/пароль, кнопки, ссылки, Google/SMS-вход),
   их тексты и состояния, **затем вводит логин/пароль реального тестового аккаунта и нажимает
   Continuă**, проверяет переход на `my.orange.md` и появление блока профиля, читает cookie
   `MyoWeb.BrowserSessionId` и сохраняет его для последующей сверки (см. "Проверка уникальности
   session id" ниже). Аккаунты берутся из `data/pages.csv` (см. "Тест-данные" ниже).
2. **Нагрузочный тест** (`load/scenario.js`, suite `api-load`) — редкая контролируемая нагрузка
   на ту же страницу логина: 1 запрос каждые 5 секунд, 60 секунд (≈12 запросов). Это НЕ тест
   API — у Orange нет отдельного API, который мы бы тестировали, поэтому "нагрузка" здесь
   означает "переоткрываем ту же HTML-страницу", а не JSON-эндпоинт.

## Файлы проекта

- `project.config.ts` — environments (только `production`), бюджеты (`pageReadyMs: 30000`,
  `elementReadyMs: 3000`), UI-профиль `smoke` (интервал старта между аккаунтами 5 секунд).
  Ни аккаунтов, ни настроек нагрузки здесь нет — см. `data/pages.csv` и `load/scenario.js`.
- `data/pages.csv` — тест-данные: колонки `login,password`, по строке на аккаунт.
  Файл в `.gitignore` (пароли не коммитим), в git лежит только `data/pages.csv.example`.
  Читается через `core/data.ts` (`readCases`), путь передаётся флагом `--data`.
- `pages/LoginPage.ts` — Page Object: локаторы элементов формы + профиля после входа
  (`profileIndicator`), методы проверки (`checkTitle`, `checkEmptyInputs`, `checkContinueButton`,
  `checkCreateAccountButton`), действие `login()`, проверка `expectLoggedIn(origin)` (домен берётся из адреса окружения) и чтение
  `sessionId()` из cookie.
- `tests/ui/login-form.spec.ts` — сам тест, по одному на аккаунт, с явными шагами Allure.
- `sessionLog.ts` — общий журнал session id за прогон (пишет каждый тест, читает `after-run.ts`).
  Не общая инфраструктура фреймворка — только этот проект знает про этот cookie.
- `after-run.ts` — запускается автоматически `core/cli.ts` после тестов (см. "after-run hook"
  в `docs/CONTEXT.md`): сравнивает все собранные session id и дописывает в результат каждого
  теста логина в Allure шаг «Session id уникален среди всех логинов прогона». Тесты с совпавшим
  session id помечает упавшими, остальные не трогает.
- `load/scenario.js` — k6-сценарий, см. ниже.

## Тест-данные

Логины и пароли — это тест-данные, поэтому они лежат в CSV (`data/pages.csv`), а не в
переменных окружения: по строке на аккаунт, одна строка = один тест. Чтобы добавить аккаунт,
достаточно дописать строку — код не меняется.

Сам файл в `.gitignore`, в репозитории только `data/pages.csv.example`. То есть механизм
привычный (CSV + флаг `--data`), но пароли в git не попадают.

Не переносите эти данные в переменные окружения: env — для настроек окружения
и инфраструктуры, а перебор аккаунтов — это data-driven тест-данные.

## Проверка уникальности session id

Бизнес-правило: у разных логинов в одном прогоне `MyoWeb.BrowserSessionId` не должен совпадать.
Так как тесты параллельны и могут работать в разных процессах, сравнение "в лоб" внутри одного
теста невозможно — тест не видит cookie других тестов. Поэтому:

1. Каждый тест после входа сохраняет `{recordId, case_id, iteration, login, password, sessionId}`
   через `appendSessionRecord()` из `sessionLog.ts` — в отдельный файл на процесс (тот же приём,
   что и `core/events.ts`, поэтому параллельная запись безопасна). `recordId` тест ставит меткой
   `session_record` на свой результат в Allure — так запись и результат теста связаны однозначно,
   даже при повторах прогона.
2. `after-run.ts` запускается один раз, уже после того как ВСЕ тесты завершились (гарантируется
   тем, что `core/cli.ts` вызывает его после `await` на весь Playwright-прогон) — читает все
   записи и группирует их по `sessionId`.
3. Записи с пустым/отсутствующим `sessionId` (неудачный логин) исключены из сравнения —
   иначе два проваленных логина дали бы ложное "совпадение".
4. Затем проходит по файлам `artifacts/allure-results/*-result.json` (отчёт из них ещё не собран),
   находит тесты по метке `session_record` и в КАЖДЫЙ добавляет шаг «Session id уникален среди
   всех логинов прогона»:
   - уникален — шаг зелёный, тест не меняется;
   - совпал — шаг и тест становятся failed с сообщением «Session id совпадает с: abc1@mail.ru
     (строка 2)» и вложением «совпадения session id». Если тест уже упал по другой причине,
     его исходная ошибка не перетирается.
5. Тот же результат пишется событием `check.login.sessionIdUnique` — чтобы Grafana совпадала
   с Allure. При найденном совпадении `after-run.ts` возвращает код 1: прогон с упавшими тестами
   считается упавшим, как и при любом другом упавшем тесте.

Важно: Playwright в терминале показывает такие тесты как пройденные (✓) — он заканчивает
работу раньше, чем происходит сверка. Итоговый статус смотрите в Allure.

Если добавляете новую проверку такого рода (сквозную, "после всех тестов") — берите этот же
паттерн (record per-process → отдельный after-run скрипт), а не пытайтесь синхронизировать
состояние между параллельными тестами напрямую (через глобальные переменные это не работает
между процессами).

## Как изменить UI-проверки

Локаторы — только в `pages/LoginPage.ts` (свойства класса, CSS-селекторы в одном месте).
Сценарий (что и в каком порядке проверяем, какие метрики пишем) — в `tests/ui/login-form.spec.ts`.
Чтобы добавить новую проверку: метод в `LoginPage.ts` + `qa.step('Название шага', () =>
qa.measure('check.login.<имя>', () => loginPage.checkНечто()))` в тесте — по аналогии с уже
существующими проверками. Название шага должно явно называть, что проверяется: если тест упадёт,
по названию шага в Allure сразу видно, на чём.

## Как изменить нагрузку (`load/scenario.js`)

Все числа — прямо в файле, ничего не выносится в `project.config.ts` (core их не читает,
см. `docs/CONTEXT.md`):

```js
export const options = {
  scenarios: {
    requests: {
      executor: 'constant-arrival-rate',
      rate: 1,            // сколько запросов...
      timeUnit: '5s',      // ...за какой промежуток времени
      duration: '60s',     // общая длительность прогона
      preAllocatedVUs: 1,  // виртуальных пользователей заранее
      maxVUs: 2,           // максимум, если ответ сайта задержится
      gracefulStop: '10s',
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<5000'], // порог, при превышении — прогон считается failed
    http_req_failed: ['rate==0'],
    checks: ['rate==1'],
  },
};
```

Чтобы изменить скорость/длительность — меняете `rate`/`timeUnit`/`duration` здесь же и всё.
**Перед тем как повышать нагрузку** — помните, что это реальный сайт: согласуйте с владельцем
проекта, прежде чем ставить rps выше учебных значений.

## Как создать альтернативный/другой сценарий

Текущее ограничение фреймворка: `core/cli.ts` всегда запускает ровно один файл —
`projects/orange/load/scenario.js`. Встроенного выбора "какой сценарий запустить" нет.
Варианты, если нужен второй сценарий (например, "спайк" вместо ровной нагрузки):

1. **Самый простой** — просто изменить `scenario.js` под новую задачу, когда она нужна
   (например, временно поднять `rate` для разового спайк-теста, потом вернуть обратно).
   Подходит, если сценарии не нужны одновременно.
2. **Держать несколько файлов, копировать нужный в `scenario.js` перед прогоном** —
   например `load/soak.js`, `load/spike.js` как черновики, и `cp load/spike.js
   load/scenario.js` перед `npm run qa -- --suite api-load`. Просто, но ручной шаг.
3. **Запустить альтернативный файл k6 напрямую, в обход `core/cli.ts`** —
   `k6 run projects/orange/load/spike.js` — сработает, но тогда результат **не попадёт**
   в Allure и Grafana (эту интеграцию делает `core/cli.ts`, а не k6 сам по себе). Годится
   для разового ручного эксперимента, не для постоянного использования.
4. **Добавить в `core/cli.ts` флаг вида `--load <имя-файла>`** — это реальное расширение
   ядра (небольшое, но осознанное решение архитектуры), которое пока не реализовано.
   Если оно нужно на постоянной основе — стоит явно попросить об этом, а не предполагать,
   что оно уже есть.

Не изобретайте пятый вариант с передачей настроек нагрузки обратно через
`project.config.ts`/`core/config.ts` — это ровно та связанность core↔project, которую
недавно убрали из фреймворка (см. "История решений" в `docs/CONTEXT.md`).
