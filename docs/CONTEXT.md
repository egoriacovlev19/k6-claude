# Контекст проекта (для ИИ и новых участников)

Прочитайте этот файл первым, если видите репозиторий впервые. Он объясняет, зачем этот
фреймворк существует, как он устроен и что нельзя ломать. Как именно им пользоваться —
в [README.md](README.md). Стиль кода — в [AGENTS.md](AGENTS.md).

## Бизнес-контекст

Владелец проекта — QA-инженер, который тестирует сайты/API вручную и хочет автоматизировать
UI-, API- и нагрузочное тестирование в одном простом инструменте, без готовых enterprise-решений
(TestNG/JMeter GUI и т.д.), и с полным контролем над кодом.

Требования, с которых стартовал проект (исходное ТЗ пользователя, дословно по смыслу):

- Enterprise-структура: конфигурация **фреймворка** отдельно от конфигурации **тестируемого
  проекта**. `core/` — auth, helpers, репортинг, сбор статистики. `projects/<name>/` — сам сайт
  или API (например, `eshop`, `accountmanagementAPI`) со своими тестами и конфигом.
- UI + API функциональное тестирование через Playwright, плюс нагрузочное тестирование через k6
  (как JMeter, но в k6): для каждого проекта — своя папка/файл, где явно прописано, какая нагрузка
  нужна (например, "10 запросов в секунду по всей тест-дате" или "20 запросов в секунду 5 минут").
- Простой Page Object Model: locators — methods — tests, ничего лишнего.
- Код должен читаться как написанный джуном: явно, без скрытой магии, с комментариями на русском
  там, где поведение неочевидно. Не в смысле "плохо", а в смысле "легко войти в контекст и поправить".
- Два инструмента отчётности:
  1. **Allure 2** — с параметрами каждой итерации (test data, login, url и т.д.), и обязательными
     вложениями при падении: screenshot, исходная ошибка Playwright, обработанная ошибка фреймворка,
     контекст (URL, CSV-данные, уже собранные метрики). Шаг Allure должен явно называть элемент/проверку,
     на которой тест упал.
  2. **Grafana + Prometheus** — без базы данных: метрики складываются в файл (`artifacts/metrics.prom`),
     маленький exporter отдаёт его наружу, Prometheus скрейпит.
- Рассчитано на **локальный запуск**: очистить старые артефакты → поднять Docker (Grafana/Prometheus,
  без БД) → прогнать тесты → собрать статистику → открыть Allure и Grafana. Отдельная команда для
  удаления старых артефактов — обязательна.
- CI/CD в этом репозитории намеренно нет — если понадобится, его добавляют отдельно (DevOps).

Первый (и пока единственный) реальный тестируемый проект — **Orange** (`projects/orange`,
`https://my.orange.md/`) — страница логина. Это авторизованная QA-работа пользователя,
не сторонний/непроверенный таргет. UI-тест открывает форму, проверяет её элементы, затем
реально входит под тестовыми аккаунтами (параллельно, со стартовым интервалом между аккаунтами)
и сверяет session id между ними. k6-сценарий даёт на ту же страницу редкую контролируемую
нагрузку (1 запрос/5 секунд, 60 секунд) — тоже авторизовано.
**Не увеличивайте эту нагрузку и не добавляйте новые нагрузочные сценарии на реальные сайты
без явного запроса пользователя** — это не тестовая песочница, а боевой сайт.

## Технический контекст

Стек: **TypeScript (Node.js, ESM, `tsx` без сборки) + Playwright + k6 + Allure 2 +
Prometheus/Grafana (в Docker, без БД)**. Пользователь изначально упоминал Go как часть
стека — в реализации Go не участвует (Playwright — TS/JS-инструмент, k6-скрипты — свой JS
рантайм); стек де-факто TS+Playwright+k6, это не пересматривалось намеренно, а сложилось
естественно. Стоит держать в уме на случай, если пользователь спросит, куда делся Go.

### Главный архитектурный принцип: `core/` не знает про конкретные проекты

`core/` — общий рантайм фреймворка. Он не содержит ни одного упоминания `orange` или любого
другого имени проекта, не хранит числа нагрузки, не знает деталей конкретного сайта/API.
Всё, что специфично для сайта/API, живёт **внутри** `projects/<name>/`. Это осознанное решение,
принятое и укреплённое в ходе ревью (были случаи, когда `core/cli.ts` собирал k6-опции —
это убрано, см. "История решений" ниже). Если правите `core/` и тянетесь добавить туда что-то
специфичное для одного проекта — скорее всего, это не туда кладётся.

### Карта `core/`

- **`cli.ts`** — точка входа (`npm run qa`). Разбирает аргументы (`--project --env --suite
  --profile --data`), загружает и валидирует конфиг проекта, чистит/готовит `artifacts/`,
  запускает Playwright (suite `ui`/`api`) или k6 (`api-load`), затем — если у проекта есть
  файл `after-run.ts` — запускает его (см. "Контракт между core/ и проектом" ниже), и в
  `finally` собирает Allure-отчёт и `metrics.prom` — независимо от того, упали тесты или нет.
- **`config.ts`** — тип `ProjectConfig` (environments, timeoutMs, budgets, profiles.*.ui) и его
  валидация (`validate()`). Жёстко ограничивает `elementReadyMs` максимумом 3000 мс — это
  сознательное бизнес-правило фреймворка, а не случайная цифра.
- **`data.ts`** — чтение CSV тест-данных (`readCases`) через `csv-parse`. `case_id` не обязателен
  в CSV — если не указан, берётся номер строки; если указан, должен быть уникальным. Также
  проверяет валидные HTTP(S) URL.
- **`events.ts`** — `saveEvent()` пишет одно событие (метрику или результат теста) в JSONL,
  один файл на процесс (`artifacts/events/<pid>.jsonl`). **Важно**: читает `QA_RUN_ID`,
  `QA_PROJECT`, `QA_ENV`, `QA_SUITE` из `process.env` напрямую, а не из аргументов функции.
- **`prometheus.ts`** — `writePrometheusFile()` перечитывает все JSONL из `artifacts/events/`
  и пересобирает единый `artifacts/metrics.prom` (Prometheus text exposition format).
- **`errors.ts`** — `errorDetails()`, единый формат ошибки (kind/name/message/stack) для Allure
  и manifest.
- **`env.ts`** — `loadEnvFile()`: подгружает переменные из `.env`-файла в `process.env`,
  не перетирая уже заданные системные переменные. Ядро не знает, какие переменные читает
  проект — имена переменных выбирает сам проект (см. "Секреты" ниже).
- **`clean.ts`** — `npm run clean`: отдельная команда очистки `artifacts/` без запуска тестов.
- **`playwright/fixtures.ts`** — `RunContext`/`qa` fixture: `qa.step()` (шаг Allure + скриншот/
  ошибка/контекст при падении), `qa.measure()`/`qa.measureElements()` (замер времени с записью
  метрики и attach JSON), `qa.navigation()` (Navigation Timing), `qa.attach()` (произвольное
  именованное JSON-вложение для бизнес-проверок проекта, которые не сводятся к числовой метрике).
  Это ядро "junior-читаемого" API, вокруг которого пишутся все тесты.
- **`playwright/reporter.ts`** — Playwright-репортер, пишет `test.duration` через `saveEvent`
  по завершении каждого теста (включая упавшие/skipped).

### Контракт между `core/` и проектом

Каждый `projects/<name>/` обязан иметь:
- `project.config.ts` — default export, соответствующий `ProjectConfig` из `core/config.ts`
  (environments, timeoutMs, budgets.{pageReadyMs,elementReadyMs}, profiles.<name>.ui.{workers,
  durationSeconds,repeats,lineIntervalSeconds?}).
- `tests/ui/*.spec.ts` и/или `tests/api/*.spec.ts` — обычные Playwright-тесты, использующие
  `test`/`expect` из `core/playwright/fixtures.ts` (не из `@playwright/test` напрямую, чтобы
  получить `qa`-fixture).
- Если нужен `--suite api-load`: `load/scenario.js` — **самостоятельный** k6-скрипт (обычный
  `.js`, не TypeScript — k6 выполняется не в Node.js и не умеет ни то, ни другое). Он сам
  экспортирует `options` (executor, rate, duration, thresholds) и `default function`. `core/cli.ts`
  лишь запускает `k6 run` на этот файл и передаёт окружение (`QA_BASE_URL`, `QA_DATA` если был
  `--data`) — числа нагрузки core не читает и не проверяет.
- Опционально: `after-run.ts` — если файл существует, `core/cli.ts` запускает его (`node --import
  tsx`) сразу после тестов, с тем же окружением (`QA_RUN_DIR` и т.д.), и учитывает его exit code
  в общем результате прогона. Это единственная точка расширения "сделать что-то своё после всех
  тестов, до сборки Allure-отчёта" — core не знает и не должен знать, что внутри. Пример —
  `projects/orange/after-run.ts` (сверка session id между логинами).

### Секреты и тест-данные — это разные вещи

Владелец проекта провёл границу явно, её нужно соблюдать:

**Тест-данные** (логины и пароли, по которым тест перебирает аккаунты) — это data-driven
входные данные теста, они живут в CSV: `projects/<name>/data/*.csv`, читаются через
`core/data.ts` и флаг `--data`. Одна строка = один тест. Переносить их в переменные
окружения не нужно — перебор строк это работа тест-данных, а не конфигурации.

**Настройки окружения и инфраструктуры** (адреса, порты, доступы к сервисам, пути к бинарникам)
— в переменных окружения с префиксом `K6_PERFORMANCE_`:

- значения берутся из системных переменных окружения **или** из файла `.env.k6_performance`
  в корне (он в `.gitignore`);
- системные переменные в приоритете: если переменная задана в системе, значение из файла
  игнорируется — поэтому один и тот же код работает и локально, и на рабочей машине;
- в репозиторий коммитится только шаблон `.env.k6_performance.example`;
- механика чтения файла — общая (`core/env.ts`), конкретные имена переменных знает проект.

**В git ничего из этого не попадает.** И CSV с паролями, и `.env.k6_performance` — в `.gitignore`,
коммитятся только шаблоны `*.example`. Сканеры секретов (GitGuardian) в репозитории
ничего не находят.

### Жизненный цикл одного прогона (`npm run qa -- --project X ...`)

1. `parseCliArgs()` — валидирует флаги.
2. `loadProject()` — динамически импортирует `projects/X/project.config.ts`, валидирует.
3. Для `api-load` — проверка, что `projects/X/load/scenario.js` существует (иначе понятная
   ошибка, а не k6 "file not found").
4. `readCases()` — CSV валидируется ДО подготовки папки запуска (fail fast).
5. `prepareRunDirectory()` — очищает **содержимое** `artifacts/`, саму папку не трогает (см.
   инвариант про Docker ниже).
6. `buildRunEnv()` + `Object.assign(process.env, env)` — переменные `QA_*` кладутся и в объект
   для дочерних процессов, и в `process.env` текущего процесса (см. инвариант ниже).
7. Запуск: `runPlaywrightSuite()` (спавнит `playwright test`, при `durationSeconds>0` повторяет
   батчами до дедлайна) или `runApiLoad()` (спавнит `k6 run`, парсит summary, пишет Allure-результат
   через `allure-js-commons/sdk/reporter`).
8. В `finally`, до сохранения статуса: `runAfterHook()` — если у проекта есть `after-run.ts`,
   запускает его и учитывает его exit code в общем результате прогона.
9. Manifest (`artifacts/run.json`) обновляется статусом, `writePrometheusFile()` пересобирает
   метрики, `generateAllureReport()` генерирует HTML-отчёт — **всегда**, даже если тесты (или
   `after-run.ts`) упали. Это осознанное поведение: провал — нормальный результат прогона,
   а не сбой инструмента.

## Инварианты — не трогать без веской причины

Эти вещи уже один раз ломались в ходе разработки. Если что-то из этого захочется "упростить" —
сначала перечитайте, почему оно так сделано.

1. **`artifacts/` — саму папку никогда не удалять и не пересоздавать, только её содержимое.**
   `docker-compose.yml` монтирует `./artifacts` в контейнер `metrics-exporter` как bind mount,
   который привязан к конкретному inode директории на момент старта контейнера. `rm -rf artifacts
   && mkdir artifacts` создаёт новый inode — контейнер продолжает смотреть в удалённую директорию
   и отдаёт "no test results yet", а Grafana показывает "No data", хотя на хосте всё есть.
   `core/cli.ts` (`prepareRunDirectory`) и `core/clean.ts` чистят только содержимое папки.
2. **`Object.assign(process.env, env)` в `cli.ts` обязателен.** `core/events.ts` читает
   `QA_RUN_DIR`/`QA_RUN_ID`/... прямо из `process.env`, а не из аргументов. `cli.ts` сам вызывает
   `saveEvent()` в своём процессе (событие `run.started`, метрики k6) — без этой строки эти вызовы
   падают с "Run tests using npm run qa", хотя тесты запущены правильно.
3. **`budgets.elementReadyMs` не может быть больше 3000 мс** — проверяется в `core/config.ts`.
   Это правило фреймворка ("любой элемент ждём максимум 3 секунды"), а не баг.
4. **Grafana Stat-панели без явного `fieldConfig.thresholds` красятся в красный при значении
   ≥ 80** (дефолт Grafana). Любая новая панель-счётчик должна явно задавать `thresholds`/`color`,
   иначе цвет не будет отражать смысл метрики (см. `infra/grafana/dashboards/qa.json`, панели
   "Passed events"/"Failed events" как пример правильной настройки).
5. **k6-скрипты — только чистый JS, без TypeScript и без импортов из `core/`.** k6 выполняется
   в собственном (не-Node) рантайме на Go и не может исполнять `.ts` или подключать пакеты из
   `node_modules`. Обмен данными между Node-частью и k6 — только через переменные окружения
   (`QA_BASE_URL`, `QA_DATA`) или CSV-файл, который k6-скрипт сам открывает через `open()`.
6. **Никаких логинов, паролей и токенов в файлах репозитория.** Только переменные окружения
   плюс gitignored `.env.k6_performance` (см. "Секреты" выше). Пароли при этом спокойно попадают
   в Allure-вложения — но отчёт лежит в `artifacts/`, а он тоже в `.gitignore`.

## История решений (чтобы не переизобретать и не возвращать удалённое)

- **Убран проект `projects/demo`** (фейковый локальный HTTP-сервер + login-страница для
  самопроверки фреймворка). Пользователь счёл его лишним шумом рядом с реальным `orange`.
- **Убран `.github/workflows/qa.yml` (CI)** — пользователь явно попросил "чистый фреймворк",
  CI/CD — забота DevOps, не этого репозитория.
- **Убраны `tests/` (юнит- и интеграционные тесты самого фреймворка)** — по прямой просьбе
  пользователя ("не нужны юнит тесты для проекта").
- **Убран `core/k6/csv.js`** (helper для чтения CSV внутри k6) — был добавлен превентивно, но
  оказался нигде не используемым (dead code) после того, как нагрузочный конфиг переехал в
  сам k6-скрипт проекта. Если понадобится CSV-driven нагрузка — парсер пишется внутри
  `projects/<name>/load/scenario.js`, а не в `core/`.
- **`load/api.js` переименован в `load/scenario.js`**, а вся сборка k6 `options`
  (`executor`, `rate`, `thresholds`) убрана из `core/cli.ts` внутрь самого скрипта. Раньше
  core собирал k6-настройки из `project.config.ts` (`profiles.*.api`, `budgets.apiP95Ms`)
  и передавал их через `QA_K6_OPTIONS` — это была скрытая привязка ядра к параметрам
  конкретного проекта. Имя `api.js` вдобавок вводило в заблуждение: файл грузит обычную
  веб-страницу, а не API.
- **`README.md`/`AGENTS.md` перенесены в `docs/`**, в корне остались короткие
  файлы-указатели (нужны, чтобы инструменты/ИИ, которые ищут `README.md`/`AGENTS.md`
  именно в корне репозитория, всё ещё их находили).
- **Логины/пароли Orange убраны из `projects/orange/data/pages.csv`** (файл удалён вместе
  с папкой `data/`) и переехали в переменные окружения — см. "Секреты". Раньше креды лежали
  прямо в CSV в репозитории, что сканеры секретов справедливо считают утечкой. Флаг `--data`
  у Orange больше не используется; сам механизм CSV в ядре остался и доступен другим проектам.

## Известные ограничения (осознанно не реализовано)

- **Один k6-сценарий на проект.** `core/cli.ts` всегда запускает ровно
  `projects/<name>/load/scenario.js` — нет флага для выбора другого файла. Если проекту
  нужно несколько разных нагрузочных сценариев одновременно — это не встроено (см.
  `projects/orange/CONTEXT.md`, раздел про создание альтернативных сценариев).
- **Нет общего `core`-модуля авторизации** (auth/helper для логина с токеном/сессией),
  хотя это упоминалось в исходном ТЗ как пример содержимого `core/`. Пока ни одному проекту
  это не понадобилось; добавлять стоит только когда появится реальный проект с этой потребностью.
- **CSV-parser для k6 — не общий.** Если проекту нужна data-driven нагрузка (как в JMeter),
  парсер CSV пишется прямо в `load/scenario.js` этого проекта (несколько строк, без внешних
  библиотек — k6 не может делать сетевые `import` по умолчанию).
